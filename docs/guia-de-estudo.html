O que a aplicação faz

Ela busca partidas em uma fonte, guarda em um banco e responde perguntas sobre elas por uma API REST. Uma página HTML consome essa API e mostra tabela, gráficos e previsões.

O caminho de um dado tem dois sentidos, coleta e consulta:

flowchart LR
  F[CSV ou API
football-data] --> P1[FonteDePartidas]
  P1 --> C[ColetarPartidas]
  C --> R[(RepositorioDePartidas
banco)]
  N[Navegador] --> API[Controller]
  API --> UC[Caso de uso
Consultar / Prever]
  UC --> R
  UC --> CALC[Calculadora
ou modelo]

Quase todo o resto do guia explica por que existem tantas caixinhas em vez de um controller que faz tudo.

4

Conceitos da parte 1

Records e validação no construtor

Um record é uma classe imutável: o Java gera construtor, equals, hashCode e toString. O construtor compacto roda antes de os campos serem atribuídos:

public record Placar(int golsMandante, int golsVisitante) {
    public Placar {
        if (golsMandante < 0 || golsVisitante < 0) {
            throw new IllegalArgumentException("gols não podem ser negativos");
        }
    }
}

Consequência: não existe Placar inválido em lugar nenhum do sistema. Quem recebe um não precisa conferir de novo. Validar no construtor, e não em um método validar(), evita que alguém esqueça de chamar.

Imutabilidade

Nenhum objeto de domínio muda depois de criado. LinhaDaClassificacao.comJogo(...) cria uma linha nova em vez de somar na atual. Isso elimina bugs de dois lugares alterando o mesmo objeto e deixa o objeto seguro entre threads.

Arquitetura hexagonal (portas e adaptadores)

Uma regra só: as dependências apontam para dentro.

flowchart LR
  api --> aplicacao
  infraestrutura --> aplicacao
  aplicacao --> estatistica
  aplicacao --> previsao
  estatistica --> dominio
  previsao --> dominio
  • Porta: interface definida por quem precisa dela. aplicacao precisa de partidas, então aplicacao declara FonteDePartidas.
  • Adaptador: implementação da porta para uma tecnologia. FonteArquivoCsv e FonteFootballData são dois adaptadores da mesma porta.

O ganho aparece nos testes: ColetarPartidasTest testa a coleta usando uma lambda como fonte e uma lista como banco. O custo também é real: mais arquivos e mais conversões. Em um CRUD pequeno seria exagero; aqui vale porque o projeto vai receber novas fontes, modelos e mensageria.

Injeção de dependência

Nenhuma classe cria as próprias dependências com new; todas recebem pelo construtor. Quem monta tudo é CasosDeUsoConfig, com métodos @Bean. Os casos de uso nem têm @Service: eles não sabem que o Spring existe.

SOLID no código

LetraPrincípioOnde ver
SUm motivo para mudarO controller só muda se o HTTP mudar; a calculadora, só se a regra da tabela mudar.
OAberto para extensãoFonte nova ou modelo novo é classe nova; nenhum caso de uso é editado.
LImplementações intercambiáveisOs testes trocam a fonte real por uma lambda e tudo funciona.

DDepender de abstraçõesaplicacao define a interface; infraestrutura implementa.

Três classes para "a mesma coisa"

Partida (domínio), PartidaEntity (banco) e PartidaResponse (JSON) mudam por motivos diferentes. Renomear uma coluna mexe só na entidade; mudar o JSON mexe só no DTO; e o domínio fica livre das exigências do JPA (construtor vazio, campos mutáveis).

Flyway e ddl-auto=validate

O Flyway cria e evolui as tabelas executando V1__...sql, V2__...sql em ordem, e registra o que já rodou. O Hibernate só confere se as entidades batem com o banco. Regra de ouro: migração aplicada nunca é editada; para mudar a tabela, cria-se outra.

Coleta idempotente

Coletar duas vezes não duplica partidas. Cada partida tem idExterno (o id dela na fonte), único no banco. Ao salvar, as que já existem são atualizadas e as novas são inseridas.

Configuração fora do código

  • @ConfigurationProperties transforma futebol.coleta.* em um record tipado.
  • O Spring lê variáveis de ambiente: SPRING_DATASOURCE_URL vira spring.datasource.url. O mesmo jar usa H2 no PC e PostgreSQL no Docker.
  • @ConditionalOnProperty decide qual fonte existe, sem if espalhado.
  • O token da API só entra por variável de ambiente, nunca em arquivo.

Tratamento de erros

O controller não tem try/catch. TratadorDeErros transforma dado inválido em 400 e falha da fonte externa em 502, no formato padrão application/problem+json.

Nenhuma classe da parte 1 precisou ser reescrita. Só CasosDeUsoConfig e o controller ganharam linhas. É a arquitetura funcionando como prometido.

A ideia do modelo de Poisson

Gols são eventos raros ao longo de 90 minutos. Eventos assim seguem bem a distribuição de Poisson: dada uma média esperada λ (lambda), ela dá a chance de sair 0, 1, 2, 3 gols. Com λ = 1,5, sair 1 gol é o mais provável (33%), depois 2 gols (25%) e 0 gols (22%).

O modelo só precisa de um λ para cada time em cada jogo:

λ mandante  = média da liga em casa × ataque em casa do mandante × defesa fora do visitante
λ visitante = média da liga fora    × ataque fora do visitante  × defesa em casa do mandante

Ataque e defesa são relativos à média: ataque 1,3 é marcar 30% acima da média; defesa 0,8 é sofrer 20% menos. Casa e fora são separados porque o mando de campo pesa no futebol.

Com os dois λ, o código calcula a chance de cada placar de 0 x 0 a 10 x 10 e soma: todos os placares com mais gols do mandante viram a chance de vitória dele, e assim por diante. São umas 30 linhas em ModeloPoisson.prever.

Previsão real do dashboard para a rodada 10:

Porto Real x Serrano, placar mais provável 1 x 1:

40%27%33%

Repare: o placar mais provável é empate, mas o resultado mais provável é vitória do mandante. Não é contradição. 1 x 1 é o placar individual mais provável, mas a soma de 1 x 0, 2 x 0, 2 x 1, 3 x 1 e todos os outros placares de vitória do mandante supera a soma dos empates.

Regularização: não acreditar demais em poucos jogos

Um time que jogou uma vez em casa e fez 6 x 0 pareceria ter quatro vezes o ataque médio. Ninguém acredita nisso depois de um jogo. Por isso cada time começa com dois jogos imaginários exatamente na média:

taxa = (gols reais + 2 × média) / (jogos reais + 2)

Com 1 jogo, os imaginários pesam muito; com 30, quase nada. Esse "puxar para a média quando há pouco dado" é a regularização, presente em quase todo modelo de machine learning.

Um teste que falhou e ensinou

O teste da regularização falhou na primeira versão, e o errado era o teste, não o modelo. Ele comparava o ataque do time contra um adversário real, cuja defesa também era puxada para a média, e os dois efeitos se misturavam. A correção foi usar um adversário sem jogos (força neutra). Quando um teste falha, primeiro descubra quem está errado: o código ou o teste.

Treinar e prever são separados

treinador.treinar(historico) devolve um modelo, e o modelo sabe prever(partida). Separar permite treinar muitas vezes com pedaços diferentes do passado (a avaliação precisa disso) e trocar o modelo inteiro do sistema mudando uma linha em CasosDeUsoConfig.treinadorDeModelo(). É de novo o O do SOLID.

Avaliação honesta: o backtest

  1. Ordena as partidas encerradas por data.
  2. Para cada uma, treina o modelo só com as partidas anteriores a ela.
  3. Prevê aquela partida e compara com o que aconteceu.

O passo 2 é o essencial. Treinar com a partida que se quer prever é vazamento de dados: o modelo já sabe a resposta, parece ótimo no teste e falha no mundo real. O teste naoVazaODaFuturo usa um treinador espião para garantir isso.

MétricaO que mede
Taxa de acertoQuantas vezes o resultado mais provável aconteceu. Sozinha engana.
Linha de baseAcerto de quem sempre aposta no mandante. O modelo precisa ganhar disto para valer algo.
Brier scoreErro das probabilidades. 0 é perfeito; chutar 1/3 para cada resultado dá 0,667. Dizer 90% e errar custa muito mais que dizer 45% e errar.

O resultado que parece ruim e é a melhor lição

29,2%acerto do modelo
45,8%acerto de "sempre o mandante"
0,761Brier, pior que chutar (0,667)

No campeonato de demonstração, o modelo perdeu para a regra mais boba. O motivo: os placares fictícios foram gerados por uma fórmula aritmética, então não existe time forte para aprender; é ruído. O modelo procura padrão onde não há, e a avaliação denuncia.

Sem a avaliação, o dashboard mostraria previsões com cara de precisas e todas inúteis. Por isso nenhum modelo vai para produção sem comparação com uma linha de base. O próximo passo é rodar com dados reais e comparar.

Docker e Kubernetes

Esta parte foi escrita mas nunca executada, porque a máquina não tem Docker. Trate como material a validar: algum ajuste deve aparecer na primeira execução.

  • Dockerfile: dois estágios. O primeiro compila com JDK; o segundo copia só o jar para uma imagem com JRE, menor e sem ferramentas de build. Roda com usuário sem privilégios.
  • docker-compose.yml: sobe PostgreSQL e a aplicação; a aplicação espera o banco ficar saudável.
Recurso em k8s/Para que serve
NamespaceSepara os recursos do projeto no cluster
SecretUsuário e senha do banco
ConfigMapConfiguração não sensível, como variáveis de ambiente
StatefulSetO PostgreSQL, com disco e identidade estáveis
Deployment2 réplicas da aplicação, com atualização gradual
ServiceEndereço estável na frente dos pods

Três probes: startup dá tempo para subir; liveness reinicia o contêiner se falhar; readiness tira o pod do balanceamento sem reiniciar.

Decisões que têm um custo

Nenhuma é "a certa". São escolhas que você deve saber defender ou trocar.

  • Time identificado pelo nome. Simples, mas quebra se a fonte mudar a grafia.
  • placar() pode ser nulo enquanto a partida não termina; quem usa precisa checar encerrada().
  • H2 no PC, PostgreSQL em produção. Prático, mas os testes não exercitam o banco real. Testcontainers resolve.
  • Coleta automática desligada no Kubernetes. Com 2 réplicas, as duas coletariam juntas. O certo é um CronJob ou um lock.
  • O modelo treina a cada requisição. Barato com centenas de jogos; com milhares, treinar após cada coleta e guardar.
  • Gols de cada time tratados como independentes. Na vida real não são totalmente; modelos como Dixon-Coles corrigem isso nos placares baixos.

Exercícios

Fazer ensina mais que reler. Do mais fácil ao mais difícil:

Parte 1

  1. Adicione "maior goleada" ao resumo. Comece pelo teste. Descubra quais três arquivos mudam.
  2. Crie outro critério de desempate (menos derrotas, por exemplo) sem alterar a calculadora.
  3. Crie GET .../times/{nome}/partidas. Decida: o filtro fica no controller, no caso de uso ou no repositório? Por quê?
  4. Adicione a coluna estadio com uma migração V2__ e leve o campo até o JSON.
  5. Implemente uma FonteDePartidas que lê JSON local. Confirme que nenhum caso de uso mudou.

Parte 2

  1. Mude os jogos fictícios de 2 para 0 e depois para 10. O que acontece com a avaliação? Por quê?
  2. Escreva um modelo ingênuo que sempre dá 45% / 27% / 28%. Ele ganha do Poisson nos dados fictícios? O que isso diz sobre os dados?
  3. Acrescente à avaliação o Brier da linha de base, para comparar de igual para igual.
  4. Dê mais peso aos jogos recentes (dica: um peso que diminui com a idade do jogo).
